## 2. 작업·배포 방식 (지금까지 쓰던 흐름)

1. 작업 브랜치에서 수정 → 문법 확인·브라우저 테스트
2. 커밋 → 작업 브랜치 push → **배포 브랜치로 fast-forward push** → GitHub Actions "Firebase 자동 배포" 성공 확인
3. 배포 워크플로우 순서: 예약 시스템 Hosting(`hosting:main`) + Firestore 규칙 + Functions → iamcenter 사이트 확인/생성 → 홈페이지(`hosting:home`)
4. HTML·JS·CSS는 `no-cache` 헤더라 새로고침하면 바로 새 버전이 보임
5. **Storage 규칙은 저장소에 없음** — Firebase 콘솔에서 직접 관리

> Claude 프로젝트(claude.ai 채팅)에서는 git push·배포를 직접 할 수 없음. 코드는 "바뀐 파일 전체" 또는 "패치"로 받아서 Claude Code(웹/앱)나 GitHub에서 적용·push해야 운영에 반영됨.

## 3. 최근 작업 이력 (2026-10-13 ~ 10-22)

### 3-1. 보안·개인정보 (10-13)
- Firestore 규칙 강화: 쓰기 권한을 관리자·구성원(`@suwoncca.org`/`allowedUsers`)·본인 기준으로 제한
- 인트라넷(portal·notice·venue·quotation·checkouts·체크리스트)은 **관리자 전용**으로 통일
- 개인정보 분리: 공개 화면은 `publicReservations`(이름·연락처 없는 사본, Cloud Function이 자동 갱신)를 읽고, 원본 `reservations`는 관리자·본인만 읽음
- `firebase.json` hosting.ignore로 CLAUDE.md·규칙·tests·functions가 웹에 공개되지 않게 함
- Storage 규칙: 확인 당시 **전체 공개(`allow read, write: if true`)** 상태였음 → 관리자만 사진 쓰기, `venue_requests` 첨부는 생성만 허용하는 규칙을 만들어 전달함. **콘솔에 실제로 적용했는지는 확인 필요** (아래 6번)

### 3-2. 지혜홀 견적서 (10-13)
- 관리비를 숙박비처럼 박수만큼 청구, 재편집 시 체크인 날짜 불일치 수정, 같은 공간 행 세로 병합

### 3-3. 센터 공개 홈페이지 `home/` (10-13 ~ 10-15) — 이번 작업의 대부분
**기반**
- 예약 시스템과 같은 Firebase(로그인·데이터) 사용, 별도 주소 iamcenter.web.app으로 배포
- 디자인은 메인 시안 v4(`iamcenter-main-v4.html`, 저장소에는 없음) 기준으로 복원

- 게시할 때마다 이전 게시본을 `siteContentHistory`에 보관 → admin.html '버전 기록'에서 복원 가능

**편집 모드 (`home/editor.js`)**
- 글자는 눌러서 바로 수정, 사진 업로드(긴 변 2400px JPEG로 줄여 Storage `site/`에 저장), 🔗 링크 수정, 섹션 순서·숨김

- `?edit=1`로 열 때 팝업이 막히면 'Google로 로그인' 버튼 표시

## 4. 알아둘 동작 방식 (헷갈리기 쉬운 것)

- **홈페이지 층별 안내의 "덮어쓰기"**: 소개 페이지에서 편집 모드를 한 번 열면 그때의 관리자 층별 안내 내용(글·버튼)이 홈페이지 쪽(`pages.about.floorText`/`floorBtns`)으로 복사됨. 게시 후에는 **예약 시스템 관리자 화면의 층별 안내를 바꿔도 홈페이지에는 반영 안 됨** → 홈페이지 글은 홈페이지 편집 모드에서 고쳐야 함
- **중심 가치 이름**은 원과 아래 설명 제목이 같은 값 — 한쪽을 고치면 다른 쪽도 같이 바뀜
- **공연·행사**를 하나도 공개하지 않으면 What's On에 시안의 예시 카드 6개와 "※ 예시입니다"가 보임
- **예약 원본 데이터는 절대 삭제 금지** (예외: `checkouts`, 6개월 지난 예약의 `history` 축약)
- 관리자가 "+ 예약 추가"로 등록한 예약은 `userEmail`이 비어 있음 → 승인 메일 대상 아님, 이름으로 "내 예약" 매칭

## 5. 개발 시 주의사항 (실제로 겪은 문제)

- **작은따옴표 문자열 안에 `'+ 버튼'` 같은 곧은 따옴표를 넣었다가 홈페이지 전체가 안 뜬 적 있음** → 안내 문구에는 “ ” 같은 둥근 따옴표를 쓸 것. `node --check home.js`는 이 오류를 못 잡았고, 파일을 `.mjs`로 복사해서 `node --check`해야 잡힘 (home/*.js는 ES 모듈)
- 굵게 처리(`richToText`)에서 `**\n**` 병합 버그가 있었음 → 정규식 `/\*\*([ \t]*)\*\*/g`로 수정됨
- JS 캐시 때문에 옛 JS + 새 CSS가 섞여 깨진 적 있음 → 지금은 html/js/css 모두 no-cache
- `index.html`은 1만 줄 넘는 단일 파일 — 수정 후 문법 오류 반드시 확인
- 새 Firestore 기능을 추가하면 `firestore.rules`도 같이 수정하고 `tests/`의 규칙 테스트 실행
- 홈페이지에서 예약 시스템으로 가는 링크는 `https://iamreservation.web.app/...` 전체 주소로 (별도 사이트라 상대 주소가 깨짐)
- 비밀값(Firebase 토큰, Resend·알리고·카카오 키)은 GitHub Secret에만 — 채팅·코드에 쓰지 않기

**테스트 방법(Claude Code 환경)**: `home/`을 로컬 서버로 띄우고 Playwright로 열면서 `fb.js`를 가짜 모듈로 바꿔치기(가짜 관리자 로그인·가짜 Firestore 데이터, 게시 시 저장값을 `window.__saved`로 확인) → 방문자 화면·편집 모드 '변경 없음'·편집 후 저장값을 확인하는 방식으로 매번 검증했음.
